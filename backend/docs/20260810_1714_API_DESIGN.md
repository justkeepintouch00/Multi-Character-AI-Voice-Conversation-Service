## 1. 설계 목적과 범위

이 문서는 웹 클라이언트와 FastAPI 백엔드 사이의 계약을 정의한다. SQLAlchemy 모델을 외부에 그대로 노출하지 않고 Pydantic 요청·응답 스키마를 경계로 사용한다.

MVP 우선순위:

```text
Health
→ Character
→ Conversation
→ Message + Job
→ 단일 캐릭터 text PoC
→ Scene Director 2인 text PoC
→ Memory ACL
→ Scenario
→ Voice/TTS/Realtime
```

현재 미확정이며 이 문서에서 임의로 결정하지 않는 항목:

- 인증: 세션 또는 토큰
- 프런트엔드: React 또는 Next.js
- WebSocket 또는 SSE의 최종 선택
- STT/TTS/Queue 공급자
- 원본 음성 저장 여부

## 2. API와 Swagger 구현 상태

| 영역 | 상태 | Swagger 노출 |
|---|---|---|
| `GET /health` | 구현·테스트 완료 | 예 |
| `GET /health/db` | 구현·테스트 완료 | 예 |
| Character | 계약 설계 완료 | 아니요 |
| Conversation | 계약 설계 완료 | 아니요 |
| Message/Job | 계약 설계 완료 | 아니요 |
| Memory | 계약 설계 완료 | 아니요 |
| Scenario | 계약 설계 완료 | 아니요 |
| Realtime | 후보 설계 | 아니요 |

Swagger는 FastAPI에 실제 등록된 route만 표시한다. 설계 문서에만 있는 endpoint를 구현된 것처럼 Swagger에 노출하지 않는다.

## 3. 공통 규칙

### 3.1 URL과 데이터 형식

- 기능 API prefix: `/api/v1`
- 운영 상태 API: `/health`, `/health/db`
- body: `application/json`
- ID: UUID 문자열
- 시간: timezone이 포함된 ISO 8601
- enum: DB 제약과 동일한 대문자 문자열
- 목록: cursor pagination

목록 응답 공통 형식:

```json
{
  "items": [],
  "next_cursor": null,
  "has_more": false
}
```

쿼리 파라미터:

| 이름 | 타입 | 기본값 | 제약 |
|---|---|---:|---|
| `limit` | integer | 20 | 1~100 |
| `cursor` | string/null | null | 서버가 발급한 opaque cursor |

### 3.2 오류 형식

```json
{
  "error": {
    "code": "RESOURCE_NOT_FOUND",
    "message": "요청한 리소스를 찾을 수 없습니다.",
    "details": {},
    "request_id": "req_01..."
  }
}
```

| HTTP | 사용 조건 |
|---:|---|
| 200 | 조회·수정 성공 |
| 201 | 동기 리소스 생성 성공 |
| 202 | 비동기 작업 접수 성공 |
| 204 | 삭제 또는 본문 없는 성공 |
| 400 | 요청 의미가 잘못됨 |
| 401 | 인증 정보 없음·실패 |
| 403 | 리소스 또는 공개 권한 없음 |
| 404 | 리소스 없음 |
| 409 | 중복·현재 상태 충돌 |
| 422 | Pydantic 필드 검증 실패 |
| 503 | DB 또는 필수 외부 서비스 사용 불가 |

오류에 connection string, password, API key, 내부 stack trace를 포함하지 않는다.

### 3.3 인증 경계

인증 방식은 미확정이다. 기능 API는 최종적으로 요청에서 확인된 `current_user`를 사용해야 하며, body의 임의 `user_id`만 신뢰해서는 안 된다.

Swagger에서 사용자 범위 API를 실제 테스트하려면 다음 중 하나를 별도로 결정해야 한다.

1. 개발 전용 `X-User-Id` header
2. JWT bearer token
3. 서버 session cookie

개발 전용 header는 생산 환경에서 비활성화해야 한다.

## 4. Health API — 구현 완료

### `GET /health`

외부 의존성과 무관한 liveness 검사다.

```json
{
  "status": "ok",
  "service": "character-companion-backend"
}
```

### `GET /health/db`

PostgreSQL에 연결하여 `SELECT 1`을 실행하는 readiness 검사다.

성공 `200`:

```json
{"status": "ok", "database": "connected"}
```

실패 `503`:

```json
{"status": "error", "database": "disconnected"}
```

## 5. Character API

외부 `character` resource는 내부의 `character_templates`, `character_versions`, `character_instances`, profile을 조합한 aggregate다.

| Method | Path | 응답 | 설명 |
|---|---|---:|---|
| POST | `/api/v1/characters` | 201 | 캐릭터 생성 |
| GET | `/api/v1/characters` | 200 | 내 캐릭터 목록 |
| GET | `/api/v1/characters/{character_id}` | 200 | 캐릭터 상세 |
| PATCH | `/api/v1/characters/{character_id}` | 200 | 새 캐릭터 버전 생성 |
| POST | `/api/v1/characters/{character_id}/archive` | 200 | 사용자 instance 보관 처리 |

### 생성 요청

```json
{
  "name": "루미",
  "nickname": null,
  "concept": "오래된 골목에서 시계 공방을 운영하며 밤에는 혼자 산책하는 캐릭터다.",
  "traits": ["다정한", "차분한"],
  "speech_style": {
    "honorific": true,
    "response_length": "MEDIUM"
  },
  "relationship_style": "FRIEND",
  "voice_sample_id": null,
  "appearance_asset_id": null,
  "additional_prompt": "",
  "visibility": "PRIVATE"
}
```

검증:

- `name`: 1~100자
- `concept`: 50~200자
- `traits`: 1~4개, 중복 금지
- `visibility`: `PRIVATE`, `UNLISTED`, `PUBLIC`
- PATCH는 기존 version을 덮어쓰지 않고 새 version을 생성

### 생성 응답

```json
{
  "id": "uuid-character-instance",
  "template_id": "uuid-template",
  "version_id": "uuid-version",
  "name": "루미",
  "nickname": null,
  "concept": "오래된 골목에서 시계 공방을 운영하며 밤에는 혼자 산책하는 캐릭터다.",
  "traits": ["다정한", "차분한"],
  "visibility": "PRIVATE",
  "created_at": "2026-08-10T17:14:00+09:00"
}
```

## 6. Conversation API

| Method | Path | 응답 | 설명 |
|---|---|---:|---|
| POST | `/api/v1/conversations` | 201 | 대화 생성 |
| GET | `/api/v1/conversations` | 200 | 내 대화 목록 |
| GET | `/api/v1/conversations/{conversation_id}` | 200 | 대화 상세·참여자 조회 |
| POST | `/api/v1/conversations/{conversation_id}/complete` | 200 | 대화 완료 처리 |
| POST | `/api/v1/conversations/{conversation_id}/archive` | 200 | 대화 보관 처리 |

### 생성 요청

```json
{
  "mode": "TALK",
  "scenario_id": null,
  "character_instance_ids": [
    "00000000-0000-0000-0000-000000000001",
    "00000000-0000-0000-0000-000000000002"
  ]
}
```

검증:

- `mode`: `PRACTICE`, `SCENARIO`, `TALK`
- 참여자: 최소 1명, schema상 최대 3명
- 2026-09-02 MVP 활성화: 최대 2명
- 같은 캐릭터 중복 금지
- `PRACTICE`, `SCENARIO`에는 유효한 `scenario_id` 필요
- 소유하지 않았거나 접근할 수 없는 character instance는 403

## 7. Message API와 비동기 Job

| Method | Path | 응답 | 설명 |
|---|---|---:|---|
| POST | `/api/v1/conversations/{conversation_id}/messages` | 202 | 사용자 메시지·AI 작업 접수 |
| GET | `/api/v1/conversations/{conversation_id}/messages` | 200 | 원본 메시지 목록 |
| POST | `/api/v1/messages/{message_id}/interrupt` | 200 | 확정된 사용자 발화로 AI 재생 중단 |
| GET | `/api/v1/jobs/{job_id}` | 200 | 작업 상태·결과 조회 |
| POST | `/api/v1/jobs/{job_id}/cancel` | 200 | 작업 취소 요청 |

### 사용자 메시지 요청

```json
{
  "content": "오늘 면접에서 떨어져서 마음이 복잡해.",
  "input_mode": "TEXT",
  "idempotency_key": "client-generated-unique-key"
}
```

검증:

- `content`: 빈 문자열 금지
- `input_mode`: `TEXT`, `VOICE`
- 동일 사용자·동일 idempotency key는 중복 message/job을 생성하지 않음
- conversation status가 `ACTIVE`가 아니면 409

### 접수 응답 `202`

```json
{
  "message": {
    "id": "uuid-user-message",
    "speaker_type": "USER",
    "content": "오늘 면접에서 떨어져서 마음이 복잡해.",
    "finalized": true,
    "created_at": "2026-08-10T17:14:00+09:00"
  },
  "job": {
    "id": "uuid-job",
    "status": "QUEUED"
  }
}
```

Job 상태:

```text
QUEUED → RUNNING → REVIEWING → COMPLETED
                 ↘ RETRYING → FAILED
QUEUED/RUNNING → CANCELLED
```

Scene Director 확정 제약:

- `internal_agent_steps <= 5`
- `visible_ai_turns_per_user_message <= 2`
- `return_turn_to = USER` 기본

Interruption은 단순 소음이 아니라 `USER_SPEECH`가 확정된 경우에만 TTS 취소와 연결한다.

## 8. Memory API

| Method | Path | 응답 | 설명 |
|---|---|---:|---|
| GET | `/api/v1/characters/{character_id}/memories` | 200 | ACL 통과 기억 목록 |
| POST | `/api/v1/memories` | 201 | 기억 생성 |
| PATCH | `/api/v1/memories/{memory_id}/permissions` | 200 | ACL 변경 |
| DELETE | `/api/v1/memories/{memory_id}` | 204 | 기억 soft delete |

### 권한 변경 요청

```json
{
  "permissions": [
    {
      "subject_type": "CHARACTER_INSTANCE",
      "subject_id": "uuid-character-a",
      "can_know": true,
      "can_read": true,
      "can_disclose_to": false
    }
  ]
}
```

규칙:

- ACL 검사 후 embedding 유사도 검색
- `can_know`, `can_read`, `can_disclose_to` 분리
- A+B 공동 기억을 C에게 자동 부여하지 않음
- 다른 사용자의 기억은 인증 경계에서 차단

## 9. Scenario API

| Method | Path | 응답 | 설명 |
|---|---|---:|---|
| POST | `/api/v1/scenarios` | 201 | 시나리오 생성 |
| GET | `/api/v1/scenarios/{scenario_id}` | 200 | 시나리오 조회 |
| POST | `/api/v1/scenarios/{scenario_id}/runs` | 201 | 처음부터 실행 시작 |
| GET | `/api/v1/scenario-runs/{run_id}` | 200 | 실행 상태·결과 조회 |

결과 정책:

- 실제 도달한 결말만 응답
- `DID_WELL`: 잘한 부분
- `TO_IMPROVE`: 아쉬운 부분
- 도달하지 않은 결말의 제목·조건·힌트는 응답 금지
- 장면 재시도 endpoint는 만들지 않음
- 재시도는 새 scenario run으로 처음부터 시작

## 10. Realtime API 후보

```text
WS /api/v1/realtime/conversations/{conversation_id}
```

후보 event envelope:

```json
{
  "event": "assistant.text.delta",
  "conversation_id": "uuid",
  "sequence": 12,
  "occurred_at": "2026-08-10T17:14:00+09:00",
  "payload": {}
}
```

이벤트 후보:

```text
user.partial_transcript
user.final_transcript
assistant.text.delta
assistant.turn.started
assistant.turn.interrupted
tts.chunk.ready
scene.motion
job.status
```

WebSocket/SSE 선택과 payload 상세는 음성 공급자·프런트 구현 전 확정한다.

## 11. 구현 단위와 트랜잭션 경계

### Character 생성

한 DB transaction에서 다음을 생성한다.

```text
character_template
→ character_version v1
→ character_instance
→ optional voice/motion/asset link
```

중간 실패 시 전체 rollback한다.

### Message 접수

한 DB transaction에서 다음을 저장한 뒤 commit한다.

```text
user message
→ job(QUEUED)
```

commit 성공 후 queue에 job id를 전달한다. DB 저장과 queue 전달 사이의 실패 복구 방식은 Worker 도입 시 outbox pattern 포함 여부를 결정한다.

## 12. 테스트 전략

| 계층 | 테스트 |
|---|---|
| Schema | Pydantic 필드·enum·길이 검증 |
| Repository | PostgreSQL CRUD·transaction·constraint |
| API | status code·response model·권한·오류 형식 |
| Contract | `/openapi.json` snapshot 또는 breaking-change 검사 |
| Integration | Message 접수→Job 생성→결과 저장 |
| Security | Memory ACL·타 사용자 접근·secret 미노출 |

## 13. 버전 및 변경 관리

- breaking change는 `/api/v2` 또는 명시적인 migration 계획 없이는 적용하지 않는다.
- field 추가는 기본값·nullable 여부를 검토한다.
- DB migration과 API contract 변경을 같은 PR에서 검토한다.
- 구현된 endpoint만 Swagger에 노출한다.
- 문서가 여러 개일 경우 작성 시각이 가장 최근인 설계서를 기준으로 한다.
