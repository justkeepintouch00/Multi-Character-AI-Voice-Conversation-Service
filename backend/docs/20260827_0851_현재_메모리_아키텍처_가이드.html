현재 메모리 아키텍처 가이드

현재 저장·권한·검색·응답 생성·관측성 흐름을 코드 기준으로 설명한다. 앞으로의 개선 계획은 포함하지 않는다.

읽는 방법: 각 제목을 클릭하면 상세 설명, DB 필드, 간단한 구현 코드까지 펼쳐진다. 처음에는 1 → 2 → 3 → 4 순서로 읽으면 된다.

현재 메모리

한 개의 memory_items 테이블에 본문, 유형, 민감도, 소유 캐릭터, 만료·삭제 상태를 저장한다.

현재 권한

memory_acl.can_read=true인 캐릭터만 검색 결과를 받는다. 그래프 edge도 원본 메모리 ACL을 다시 확인한다.

현재 검색

의미 유사도 검색이 아니라 생성일 최신순 검색이다. 임베딩 컬럼은 있지만 현재 검색에서 사용하지 않는다.

현재 GraphRAG

관계 질문 신호가 있을 때 관계 문자열을 키워드 검색한다. 다단계 노드 탐색은 아직 하지 않는다.

핵심 사실: 현재는 별도 “대화 요약 API 호출”이 없다. 응답 생성 LLM의 구조화된 출력에 기억 후보가 포함되며, 조건을 만족할 때만 DB에 저장된다.

2. 요청 하나가 처리되는 흐름

기본 경로: 한 명의 캐릭터가 응답하는 경우
START
  → select_speakers
  → retrieve_primary_context
      → LangChain Runnable
      → ACL 허용 일반 메모리 최대 8개
      → 관계 질문 신호가 있으면 graph edge 최대 5개 추가 검색
  → generate_primary
      → LLM이 응답 text + extracted_memory를 함께 반환
  → store_primary_memory
      → has_memory=true일 때만 MemoryItem 저장
      → 관계가 명시되면 MemoryGraphEdge 저장
  → finalize
  → END

이 구조는 backend/app/workflows/conversation_graph.py의 StateGraph에 정의돼 있다.

두 명의 캐릭터가 응답하는 경우

첫 번째 캐릭터의 응답 뒤에 needs_second_speaker 또는 강제 2인 응답 조건이 참이면 다음 경로가 추가된다.

store_primary_memory
  → retrieve_secondary_context
  → generate_secondary
  → store_secondary_memory
  → finalize

한 사용자 발화에도 최대 두 번의 응답 LLM 호출과 두 번의 기억 후보 추출이 일어날 수 있다. 각 캐릭터는 자신에게 ACL로 허용된 메모리만 검색한다.

class MemoryItem(...):
    memory_type: str
    owner_character_instance_id: UUID | None
    content: str
    sensitivity: str
    embedding: list[float] | None
    expires_at: datetime | None
    deleted_at: datetime | None
memory_acl — 캐릭터별 접근 권한

한 메모리에는 사용자 또는 캐릭터 인스턴스 단위 ACL을 여러 개 둘 수 있다. 실제 검색은 캐릭터 인스턴스 ACL을 조인해서 처리한다.

필드현재 의미
subject_type / subject_id권한 대상의 종류와 식별자. 현재 값은 USER 또는 CHARACTER_INSTANCE
can_know그 기억의 존재를 알 수 있는지
can_read본문을 검색·읽을 수 있는지
can_disclose_to다른 참여자에게 공개할 수 있는지
granted_by_user_id권한을 부여한 사용자
memory_graph_edges — 기억에서 나온 관계

독립된 지식 그래프가 아니라, 특정 MemoryItem을 근거로 하는 관계 레코드다.

MemoryItem
  “사용자는 다음 주 면접이 걱정된다고 말했다.”

MemoryGraphEdge
  source_entity = “사용자”
  relation      = “걱정한다”
  target_entity = “다음 주 면접”
  memory_id     = 위 MemoryItem의 ID

memory_id + source_entity + relation + target_entity 조합은 중복 저장되지 않는다.

memory_access_logs·memory_sources
  • memory_access_logs: 누가 어떤 기억을 조회·공개·공유하려 했는지, 허용·차단됐는지, 이유가 무엇인지 기록한다.
  • memory_sources: 기억과 원본 메시지를 연결하기 위한 테이블이다.

4. ACL 규칙

일반 메모리 검색에 적용되는 실제 조건
MemoryItem.user_id == 현재 사용자
AND MemoryItem.deleted_at IS NULL
AND (expires_at IS NULL OR expires_at > 현재 시각)
AND MemoryACL.subject_type == "CHARACTER_INSTANCE"
AND MemoryACL.subject_id == 현재 응답 캐릭터
AND MemoryACL.can_read == true
ORDER BY MemoryItem.created_at DESC
LIMIT 8

현재 기본 검색은 권한이 허용된, 삭제되지 않고 만료되지 않은 기억 중 최신 8개다. 검색 결과마다 RETRIEVE / ALLOW 접근 로그가 기록된다.

권한의 의미와 공유 제안
  • can_read가 거짓이면 해당 캐릭터의 프롬프트에 메모리 본문이 들어가지 않는다.
  • can_disclose_to는 다른 참여자에게 기억을 말로 공개할 수 있는지와 관련된 권한이다.
  • LLM이 다른 캐릭터에게 실제로 말한 메모리 ID를 반환하면, 서비스는 그 ID가 이번 요청에서 해당 캐릭터에게 검색된 것이 맞는지 다시 확인한 후 공유 제안을 만든다.
  • 공유 제안 자체가 DB ACL을 자동으로 바꾸지는 않는다.
그래프 검색에도 ACL이 다시 적용되는 이유

관계 edge만 별도로 읽으면 관계를 통해 비공개 기억의 존재를 유추하는 누출이 생길 수 있다. 그래서 그래프 검색은 edge를 원본 MemoryItem에 조인하고, 다시 요청 캐릭터의 can_read=true ACL을 확인한다.

결과: 그래프 edge는 일반 메모리보다 넓은 권한을 주지 않는다.

5. 기억 생성과 “요약”의 현재 의미

현재는 별도 대화 요약 호출이 없다

현재 응답 생성 LLM은 사용자에게 보낼 text와 함께 선택적으로 extracted_memory를 반환한다. 별도의 요약 API를 호출하지 않는다.

{
  "text": "사용자에게 보낼 캐릭터 응답",
  "extracted_memory": {
    "has_memory": true,
    "content": "사용자는 다음 주 면접이 걱정된다고 말했다.",
    "sensitivity": "PERSONAL",
    "graph_relation": {
      "has_relation": true,
      "source_entity": "사용자",
      "relation": "걱정한다",
      "target_entity": "다음 주 면접",
      "summary": "면접 전 불안"
    }
  }
}

대화 전체를 압축하는 에피소드 요약이 아니라, 이번 사용자 발화에서 장기적으로 기억할 만한 사실을 한두 문장으로 재서술하는 추출에 가깝다.

LLM에 주어진 현재 기억 추출 규칙
  • 앞으로도 기억할 가치가 있는 새로운 사실일 때만 has_memory=true
  • 이미 전달된 기억을 중복 저장하지 않음
  • 사소한 잡담·일회성 감탄·추측한 감정은 저장하지 않음
  • 사용자가 실제로 말한 내용만 기록
  • 본문은 “사용자는 ~라고 말했다” 형태의 짧고 구체적인 한두 문장
  • 명시된 주체·관계·대상이 있을 때만 graph relation 생성
저장 코드가 실제로 하는 일
if not result.extracted_memory.has_memory:
    return

memory_record = memory_repository.create_memory(
    content=content,
    memory_type="RELATIONSHIP",
    sensitivity=result.extracted_memory.sensitivity,
    owner_character_instance_id=현재_응답_캐릭터,
    readable_by=공유_모드로_계산한_캐릭터들,
)

if graph_relation.has_relation:
    graph_repository.create_edge(memory_id=memory_record.id, ...)
현재 사실: 자동 추출 메모리는 본문이 선호·일정·감정처럼 보여도 현재 코드에서 RELATIONSHIP 타입으로 저장된다.

6. 기억 검색과 프롬프트 조립

일반 메모리 검색

각 응답 캐릭터마다 일반 메모리 검색을 먼저 실행한다. 결과는 ACL을 통과한 최신 메모리 최대 8개다.

memory_records = memory_repository.retrieve(
    user_id=현재_사용자,
    viewer_character_instance_id=현재_응답_캐릭터,
    conversation_id=현재_대화,
)

현재는 content·embedding 유사도, 메모리 유형별 쿼터, 토큰 예산 기반 정렬을 적용하지 않는다.

LangChain Document로 변환되는 이유

검색 결과는 LangChain의 Document로도 변환된다. 본문은 page_content, 메모리 ID·유형·민감도·출처는 metadata에 들어간다.

Document(
    page_content=record.content,
    metadata={
        "memory_id": str(record.id),
        "memory_type": record.memory_type,
        "sensitivity": record.sensitivity,
        "source": "acl_memory",
    },
)

현재 응답 프롬프트 조립은 MemoryContextItem을 사용한다. Document는 LangChain 기반 검색 경계를 만들기 위한 형식이다.

그래프 검색 결과가 일반 기억과 합쳐지는 방식

그래프 검색 결과의 원본 memory_id가 이미 일반 메모리에 있으면 중복 추가하지 않는다. 없으면 아래 문자열을 관계 기억으로 추가한다.

[관계 그래프] 사용자 —[걱정한다]→ 다음 주 면접 (면접 전 불안)

LangGraph를 쓰는 이유
  • 1명 응답과 2명 응답의 조건 분기를 코드에서 노드·edge로 명시한다.
  • 검색·생성·저장을 분리해서 노드별 시간을 기록한다.
  • 대화 순서가 한 함수에 섞이지 않아 실행 경로를 추적할 수 있다.
LangChain을 쓰는 이유
  • 현재 SQLAlchemy 검색을 Runnable이라는 호출 가능한 단위로 감싼다.
  • 검색 결과를 Document로 표준화한다.
  • ConversationWorkflow가 DB 구현 세부사항을 직접 알지 않게 한다.

Runnable은 입력을 받아 출력을 반환하는 재사용 가능한 처리 단위다. 현재는 RetrievalRequest → RetrievalBundle 변환을 담당한다.

8. 현재 부분 GraphRAG

언제 실행되는가

사용자 발화에 아래 정규식 신호 중 하나가 있을 때만 실행한다.

관계 | 사이 | 누구 | 누가 | 왜 | 이유 | 전 | 후 | 이후 | 기억 | 다시

일반 메모리 검색은 항상 실행되고, GraphRAG는 그 결과에 추가되는 조건부 검색이다.

실제로 무엇을 검색하는가
  1. 사용자 문장에서 두 글자 이상 토큰을 최대 8개 추출한다.
  2. 불용어를 제거한다.
  3. source_entity, relation, target_entity, summary에 토큰이 포함된 edge를 찾는다.
  4. 원본 메모리 ACL을 통과한 최근 edge 최대 5개를 반환한다.

현재 구현은 “관계가 담긴 메모리를 추가 검색”하는 부분 GraphRAG다. 노드 간 2홉·3홉을 따라가는 그래프 순회는 아니다.

왜 일반 검색을 대체하지 않는가
  • 일반 잡담은 최신 ACL 허용 메모리만으로도 충분할 수 있다.
  • 관계 검색은 “왜”, “누구”, “전후”처럼 관계가 필요한 질문에만 추가 근거를 제공한다.
  • 그래프 edge도 원본 ACL을 확인하므로 관계 검색이 권한 범위를 넓히지 않는다.

ACL 평가에서 “누출”을 판단하는 기준

차단 대상 캐릭터가 메모리 본문·요약·ID 중 하나라도 볼 수 있으면 누출이다. 누출이 한 건이라도 있으면 해당 ACL 결과는 통과할 수 없도록 대시보드에 명시돼 있다.

현재 평가에 없는 지표

현재 평가 대시보드에는 Context Precision, Context Recall, Groundedness, Graph Path Accuracy 같은 검색 정확도 지표는 구현돼 있지 않다.

현재 구현된 평가는 대화 품질의 사람 검토, 구조 검사, ACL 허용·차단 정확도에 초점이 있다.

  • memory_searches_total: 메모리 검색 실행 횟수
  • memory_search_result_count: 일반 메모리 검색 결과 수

Grafana에서 볼 수 없는 것
  • 메모리 원문과 민감 정보
  • 특정 사용자의 실제 관계 그래프 그림
  • ACL 허용·차단의 개별 본문
  • 요약 본문

이 내용은 Prometheus 메트릭으로 보내지지 않는다. Grafana는 운영 수치용이고, 메모리 본문을 보내지 않는 것은 개인정보 보호 측면에서 의도된 경계다.

11. 현재 범위와 제한

구현됨

  • 메모리 DB·ACL·접근 로그
  • 삭제·만료 메모리 제외
  • LangGraph 기반 대화 순서
  • LangChain Runnable·Document 경계
  • 조건부 관계 edge 검색
  • 메모리·GraphRAG 관측 지표

현재 구현되지 않음

  • 대화 단위 에피소드 요약
  • pgvector 임베딩 검색
  • 다단계 그래프 순회
  • 기억 유형별 의미 검색
  • 검색 정확도 평가 지표
  • LangGraph durable checkpoint

이 문서는 현재 코드와 대시보드 정의에서 확인한 사실만 기록한다. 구현되지 않은 항목은 계획이나 약속이 아니라 현재 범위 밖이라는 뜻이다.
